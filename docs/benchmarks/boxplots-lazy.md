# 延後建立的箱形圖（lazy plot）與大量物件的繪製流程

`boxplot`／`bxp` 不再為每個元件建立 artist：一次呼叫的座標以陣列交給 Rust 核心，
由一個批次物件直接繪製；`Line2D`／`PathPatch` 物件在第一次被讀取時才建立。
同時，Axes 內連續的線段、patch 與批次改為一起交給 Agg renderer，以多個執行緒點陣化與混色。
畫布在每一種狀態下都與官方 **Matplotlib 3.11.2 逐像素相同**。

量測對象為 commit `5a9372b`（0.0.5 之後），對照 **matplotlib-rs 0.0.5**（commit `ddf0496`）與 Matplotlib 3.11.2。

| 工作負載（中位數，秒） | Matplotlib 3.11.2 | 0.0.5 | 本次 | 對 Matplotlib | 對 0.0.5 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 5,400 箱（30 次呼叫）建圖 | 14.222 | 0.348 | **0.111** | 128× | 3.1× |
| 5,400 箱（30 次呼叫）建圖＋首次繪製 | 17.538 | 0.506 | **0.165** | 106× | 3.1× |
| 5,400 箱（30 次呼叫）重繪 | 1.557 | 0.134 | **0.041** | 38× | 3.2× |

（依序為 Matplotlib、0.0.5、本次）。

## 做了什麼

### 1. artists 在需要時才建立

0.0.3 起，`bxp` 已經一次建立全部 artists；剩下的時間幾乎都花在這些物件本身：
5,400 箱是 37,800 個 Python 物件與 37,800 個 Rust handle。多數腳本畫完就存檔，從未讀取它們。

現在每次 `bxp` 呼叫只做三件事：以 NumPy 計算座標（與 0.0.3 相同的逐元素運算）、
把座標與各元件的樣式交給 Rust 成為一個 `_mplrs.ArtistBatch`、更新資料範圍。
`Axes._children` 放入一個代表這批 artists 的 `_Pending`（`axes/_base_rs.py`）。

- **回傳值**仍是 `whiskers`、`caps`、`boxes`、`medians`、`fliers`、`means` 的 `list`。
  讀取其中一個（索引、迭代、`in`、相加、排序……）才建立**該元件**的 artists；`len()` 不會建立。
- **`ax._children`**（`ax.get_children()`、`ax.lines[i]`、`findobj` 等）被讀取時建立全部 artists，
  順序、標籤（`_child123`）、sticky edges、資料 dtype 都與在 `bxp` 內建立時相同。
- 下列流程不需要任何 artist，因此不會建立：繪製與 `savefig`（PNG／SVG／PDF／PS）、
  `autoscale_view`（含 `manage_ticks` 的 sticky edges）、`relim`、`tight_layout`、constrained layout、
  `bbox_inches="tight"`、`legend`、`len(ax.lines)`、`len(ax.patches)`、`has_data`、之後再呼叫 `plot`／`boxplot`。
  `label=` 與中位數線的 sticky edges 先記在 `_Pending`，建立時才套用；圖例只建立有公開標籤的那個元件。
- 建立出來的是一般的、可獨立修改的 artist，各有自己的 Rust handle。只要沒有任何一個被修改，
  批次物件就繼續負責繪製（**讀取不會讓繪製變慢**）。第一個被修改（標記 stale 而同步）
  或被移除的 artist，會讓該次呼叫的批次換成全部 artists 的 handle，之後逐一繪製，與 0.0.5 相同。
  其他 `boxplot` 呼叫的批次不受影響。
- `ax.clear()` 之後才讀取的 artists 沒有 Axes（如同被清除的 artist）。
- 不能延後的情況沿用在 `bxp` 內建立：artist 未裁切在 Axes 內（`clip_on=False`）、animated，
  以及原本就走逐箱路徑的情況（單位、自訂 transform、非一般浮點數統計值等）。
  `MPLRS_LAZY=0` 可停用延後建立。

`boxplot` 計算的統計值在規則浮點陣列時也保持為陣列（`cbook._BoxplotStats`），
`bxp` 直接取用；只有讀取（例如 `usermedians`、`conf_intervals`）時才建立每箱一個的 dict。
公開的 `cbook.boxplot_stats` 仍回傳一般的 dict list。

### 2. 大量物件一起繪製

Axes 依 zorder 排好後，連續的 `Line2D`、`Patch` 與批次（至少 256 個 artists）會一起交給
`RendererAgg::draw_artists`（`src/mpl/batch.rs`、`src/backend/renderer_agg.rs`），
條件是 renderer 為 Agg，且該 artist 的繪製就是一次 `draw_path` 加上一次 `draw_markers`
（仿射 transform，沒有 clip path、hatch、sketch、gapcolor、`markevery`）。
其餘 artist 與其他 renderer（SVG、PDF、PS）照舊逐一繪製，呼叫順序不變。

- **分回合**：每回合若干個連續的 artists。執行緒先各自把 artists 點陣化成掃描線紀錄，
  再依影像的水平帶（band）混色：一條帶只由一個執行緒處理，並依 artist 順序，
  所以每個像素得到的混色順序與逐一繪製相同，結果逐像素一致。點陣化與混色都平行。
- **重複的列只掃一次**：直線外框（箱體、鬚線、caps 的筆畫）在垂直邊的端點之間，每一列的 span 完全相同。
  `RasterizerScanlineAa::skip_repeated_rows` 只掃第一列並記下重複次數。
  這是單執行緒下也有的加速（見下表 `MPLRS_THREADS=1`）。
- **相同的 marker 只點陣化一次**：樣式相同的離群點共用一個 marker 圖章。
- 批次沒有逐 artist 的鎖、graphics context 與路徑配置：每個元件一份設定，頂點直接取自陣列。
- 這條路徑也用於一般的 artists（例如修改過的箱形圖、`stem`、大量 `plot`）。

`MPLRS_THREADS` 指定執行緒數（`1` 為單執行緒）；輸出與執行緒數無關。

## 量測方法

- 環境：CPython 3.13.18、NumPy 2.3.5、Matplotlib 3.11.2、Pillow 13.0.0、Rust 1.97.0、Linux x86_64、
  Intel Xeon Processor @ 2.10GHz、4 vCPU；release、fat LTO；專案的 no-hinting matplotlibrc 與 Agg。
  量測期間未同時進行編譯或其他測試。這台虛擬機各輪仍有 ±20% 左右的波動，表中附上範圍。
- 每個數值都來自全新的 Python 行程；各版本依序執行、每輪交替順序，先各暖機一次，取五輪中位數。
  資料以固定 seed 產生，不計入時間，並檢查各版本的資料雜湊相同。
- 0.0.5 由同一份原始碼樹的 commit `ddf0496` 以相同工具鏈編譯（`--python-source`／`--base-source`）。
- 原始數據：[`boxplots-lazy.json`](boxplots-lazy.json)。JSON 內的 `git_commit` 為 `ddf0496`：
  量測時本次修改尚未提交，內容即 commit `5a9372b`。

範圍（50,000 箱，最小～最大）：本次建圖 0.329～0.450、首次繪製 0.158～0.252、重繪 0.161～0.179；

怎麼讀這兩張表：

- **不讀取 artists 的流程**（建圖、繪製、存檔）是主要的受益者：50,000 箱建圖＋首次繪製
  3.3 → 0.53 秒，記憶體 1.5 GiB → 211 MiB。剩下的建圖時間一半以上是統計值的計算（NumPy 的百分位數）。
- **成本是延後，不是消失**：讀取全部 artists 時（50,000 箱 1.25 秒）才支付建立物件的時間；
  建圖加上全部讀取為 0.35 + 0.18 + 1.25 ≈ 1.8 秒，仍低於 0.0.5 的建圖 2.25 秒，
  行程結束時的最高 RSS 與 0.0.5 相近（1,548 對 1,505 MiB，多 3%）。只讀取箱體則是 0.18 秒。
- **讀取不影響繪製**：artists 存在但未修改時仍由批次繪製（50,000 箱 0.19～0.27 秒，0.0.5 為 0.9 秒）。
- **修改之後**回到逐一繪製：修改後第一次重繪要同步 50,000 個修改並交出 350,000 個 handle（1.41 秒，
  0.0.5 為 1.70 秒）；之後每次重繪 0.60 秒，比 0.0.5 的 1.23 秒快 2 倍（平行繪製與重複列）。
- **執行緒的貢獻**：`MPLRS_THREADS=1` 時 50,000 箱重繪 0.311 秒，已比 0.0.5 快 3 倍
  （重複列與沒有逐 artist 的開銷）；4 個執行緒再快 1.8 倍。
- `eager` 欄（同一份程式碼、在 `bxp` 內建立）與 0.0.5 的差異只來自繪製流程：
  50,000 箱首次繪製 1.113 → 0.645 秒。

每種箱數的 21 次執行（四個版本各五輪，加上 Matplotlib 一輪）在三個時間點
（首次繪製後、讀取後、修改後）的畫布雜湊全部相同，包含 Matplotlib 在 5,400 與 50,000 箱的畫布；
`_children`、`ax.lines`、`ax.patches` 的數量也相同。

## 限制

- 改為逐一繪製以一次 `boxplot` 呼叫為單位：修改其中一個 artist，該次呼叫的全部 artists 都改由各自的 handle 繪製
  （仍比 0.0.5 快，見上表「再次重繪」）。
- 平行繪製只用於 Agg；SVG／PDF／PS 仍逐一呼叫 renderer，速度與先前相同（但不必建立 Python 物件）。
- 讀取 `ax._children`（`get_children()`、`ax.lines` 的迭代或索引、`findobj`、pick 事件、`loc="best"` 的圖例）
  會建立全部 artists；`len()` 不會。
- 回傳的 list 是 `list` 的子類別，`type(result["boxes"]) is list` 為 `False`；`isinstance` 與所有 list 操作正常，
  pickle 與 `copy` 得到一般的 list。
- 本次未重跑完整的官方 gallery（581 支），只重跑 `statistics` 目錄。
- 數值來自單一台 4 vCPU 虛擬機，會隨 CPU、核心數與圖形大小改變；0.1 秒以下的數值各輪波動可達 20%～30%。
