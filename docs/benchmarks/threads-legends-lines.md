# 常駐執行緒、分帶混色、共享頂點與圖例

對照 [Polars](https://github.com/pola-rs/polars) 使用的效能作法（常駐的全域執行緒池、
每個執行緒獨占一個分區、共享而不複製的 buffer、不逐筆執行 Python、全域配置器、以新指令集編譯），
逐項量測哪些在本專案有用，並實作有用的部分。所有修改都必須與官方 **Matplotlib 3.11.2** 的結果相同：
24 個大量資料案例、59 個繪圖案例與本次新增的測試，畫布全部**逐像素一致**。

量測對象為 0.0.6 之後的程式碼（Rust 核心 commit `69d69ee` 加上本次的 Python 層），
對照 **matplotlib-rs 0.0.6**（commit `dbadedd`）與 Matplotlib 3.11.2。

## 做了什麼

### 1. 常駐的執行緒（[`src/pool.rs`](../../src/pool.rs)）

0.0.6 有九處平行迴圈，每次呼叫都以 `std::thread::scope` 建立執行緒。
現在執行緒只建立一次並重複使用：`pool::run(n, f)` 是一個平行區段，
在呼叫的執行緒執行 `f(0)`，在 `n - 1` 個常駐執行緒執行 `f(1)` 到 `f(n - 1)`，全部返回後才返回。

- 另一個平行區段進行中（由常駐執行緒內巢狀呼叫，或由另一個 Python 執行緒呼叫）時，
  新的區段改用臨時執行緒，不會等待或死結。
- `fork` 之後的子行程沒有父行程的執行緒：區段開始時比對行程代號，不同就建立子行程自己的執行緒。
  若 `fork` 發生在另一個執行緒的區段進行中，子行程一律使用臨時執行緒。
- 任何一個執行緒 panic，會等其他執行緒結束後在呼叫端重新拋出，之後的區段照常執行。
- 直方圖計數原本固定用「可用核心數」，沒有讀 `MPLRS_THREADS`（與 README 的說明不符）；現在所有平行迴圈都由同一個設定決定。
- 影像重採樣的列與等高線的 level 原本平均分給各執行緒；現在由各執行緒依序取用
  （影像每個執行緒四組列），工作量不均時不會有執行緒先做完而閒置。

行程在第一次平行繪製之後會多出 `MPLRS_THREADS - 1` 個閒置的執行緒（4 核心時 3 個）。
`import numpy` 本身已經讓行程有多個執行緒（OpenBLAS），所以 Python 3.12 起 `os.fork()` 的多執行緒警告不是新增的。

### 2. path collection 的混色也平行（scatter、hexbin、pcolormesh、stem）

0.0.4 的作法是各執行緒點陣化、記錄掃描線，再由**一個**執行緒依序混色。
20 萬個大小各異的 marker 在 4 執行緒只比 1 執行緒快 1.77 倍：混色的執行緒有一半時間在重播掃描線，其他執行緒在等它。

現在與 0.0.6 的 `draw_artists` 相同：一輪（每執行緒 4 × 128 條路徑）先由各執行緒點陣化並記錄，
再把影像分成水平帶，每一帶由一個執行緒依路徑順序混色。每個像素只屬於一帶，所以混色順序與單執行緒相同。

另外，Agg 的 Python 包裝層把 collection 的 transform 逐一轉成陣列，
而且 `Collection.draw` 會先以空的 paths 呼叫一次（Matplotlib 用來探測 renderer 是否接受 `hatchcolors`），
等於每次繪製轉換兩遍（20 萬個 3 × 3 矩陣合計約 0.2 秒）。現在 transform 已經是 (N, 3, 3) 陣列時直接使用，空的 paths 直接返回。

同一張 scatter 重複繪製的最小值（毫秒）：

| 執行緒 | 0.0.6 | 本次 |
| --- | ---: | ---: |
| 1 | 1,640 | 1,475 |
| 2（在不同的實體核心） | 1,439 | 954 |
| 3 | 1,088 | 907 |
| 4 | 948 | **524** |

量測用的虛擬機有部分 vCPU 共用實體核心：兩個執行緒落在同一個核心時，兩個版本都是 1.5～1.6 秒（與單執行緒相同）。

### 3. 路徑頂點放在可共享的 buffer（[`src/backend/verts.rs`](../../src/backend/verts.rs)）

`Path` 的頂點原本是各自擁有的 `Vec`。一條 `Line2D` 因此保有四份資料
（xy、x、補過 NaN 的 x、路徑頂點，每點 64 bytes），每次繪製還會把可見區段複製兩次。

`Verts` 是一段 buffer 或其中一部分：複製與切片共用同一份記憶體，寫入共享中的頂點時才複製。

- 沒有 step 的折線，路徑直接共用 xy；有 NaN 時才另存補過的 x，否則直接在 xy 上二分搜尋。
- 放大後只畫可見區段（subslice）時，區段是原 buffer 的切片，繪製不再複製任何頂點。
- 從 NumPy 轉入路徑時，連續陣列整塊複製，不再逐元素索引（等高線繪製原本有 5% 花在這裡）。

### 4. 圖例

圖例與 offsetbox 仍由 Python 層排版與繪製。profile 顯示時間花在三件重複的事：

- **最佳位置**：`Legend._find_best_position` 對 10 個候選位置逐一、對每個 artist 各呼叫數個小型 NumPy 運算
  （這張圖一次存檔 480 次 `count_contains`）。現在由 `_path.legend_badness` 一次算出所有候選的分數：
  頂點與 offset 落在候選框內的數量、重疊的 bbox 數、穿過候選框的路徑數，與原本各方法的算式相同。
  原迴圈遇到分數為 0 就停止，否則取分數最小的第一個；兩者都是「分數最小的第一個」，所以結果相同。
- **同一次繪製內重算**：`Legend.draw` 先取外框的範圍、再繪製，兩次都會找最佳位置；
  每一層 offsetbox 取自己的範圍時會重算所有子框，繪製時再算一次，一個圖例的文字（兩個項目與標題）在一次繪製中共被排版 12 次。
  `Legend.draw` 期間不會改變這些範圍所依據的任何東西（只改 offset），所以這段期間最佳位置與各框的範圍只算一次；
  繪製結束就丟棄，不跨越繪製保留。
- **字型量度**：`Text._get_layout` 每次都重新找字型檔並讀 OS/2、hhea 表（這張圖一次存檔 288 次 `findfont`）。
  現在依字型屬性、dpi、字型相關的 rcParams 與 font manager 的字型數保留結果。

### 5. violinplot 與加入 Axes 的 artist

- `GaussianKDE.evaluate`（一維、float64）一次處理約 8,000 個元素，而不是每個評估點各做一輪 NumPy 呼叫。
  每個元素經過相同順序的相同運算，每個點對資料的加總仍是 NumPy 對一列連續資料的加總，
  結果與迴圈**逐位元相同**（以 Matplotlib 的結果比對）。一次處理更多元素反而較慢：暫存陣列超出處理器快取。
- 每個加入 Axes 的 artist 都會 `set_clip_path(axes.patch)`，其中建立 patch 的 transform 占了大部分時間（約 0.1 毫秒）。
  Axes 的 patch 沒有改變時，各 artist 共用同一個 transform 物件；500 片的 pie 建圖 0.311 → 0.277 秒。

## 試過但沒有採用

- **mimalloc 作為全域配置器。** 最初的量測（同一行程重複繪製）顯示百萬點折線快 1.4 倍，
  但那來自頂點的複製，第 3 項已經消除。在相同程式碼上比較：
  - 預設參數下，全新行程的首次繪製變慢（百萬點折線 51 → 170 毫秒、20,000 根長條 32 → 96 毫秒、
    直方圖存檔 5 → 21 毫秒），最高 RSS 多 45～60 MiB；
  - 設定 `arena_eager_commit=0`、`purge_delay=1000` 後首次繪製與不用時相同，重複繪製快 0～10%
    （scatter 620 → 523 毫秒，對照組 569 毫秒），最高 RSS 仍多 5～36 MiB（含 4000 × 4000 影像的圖多 20%）。

  增益小於代價，因此維持系統配置器。
- **整個套件以 AVX2 編譯（`-C target-cpu=x86-64-v3`）。** 九個案例為 0.86～1.04 倍，沒有可量得的增益，
  不值得為此發行兩套 wheel。
- **混色的 SIMD。** 沒有實作。散佈圖的掃描線每段只有 2～6 個像素，逐像素的覆蓋率也不同，無法成批處理；
  混色在單執行緒的 scatter profile 中不到 10%，其他案例更低。
- **`savefig` 的兩次繪製。** `tight_layout()` 之後 `savefig` 會先排版繪製一次、再真正繪製一次（與 Matplotlib 相同）。
  略過第一次在繪製會改變狀態的圖上可能得到不同結果，因此保留；本次只讓兩次繪製各自變便宜。
- **pie 的延後建立。** 500 片的建圖時間平均分散在約 80 萬次 Python 函式呼叫，沒有單一熱點；
  要像箱形圖那樣延後建立 wedge 與文字，規模與 0.0.6 的箱形圖相當，本次沒有做。
- **刻度的重算。** 建圖階段 `ticks_signature` 被呼叫 164 次（約占一成），每次都重新計算刻度；
  安全地略過需要追蹤 view limits、locator 與 formatter 的所有狀態，本次沒有做。

## 驗證

- Rust 測試 33 個通過（新增執行緒池 5 個、共享頂點 2 個）。
- 既有測試全部通過：11 支單元測試、5 支底層差異測試、原生模型、
  59／59 個繪圖案例的 PNG／SVG／PDF／EPS（其中 10 個含內嵌影像的案例解碼後像素相同，與 0.0.6 相同）。
- 24 個大量資料案例在五輪中每一輪的畫布都與 Matplotlib 相同。
- 新增 [`tests/unit/test_fast_paths.py`](../../tests/unit/test_fast_paths.py)（20 個測試）：
  - 圖例：10 種場景（線、散佈點、長條、patch 與文字、對數座標、NaN、`bbox_to_anchor`、每個位置都有資料……）的
    最佳位置與原迴圈及 Matplotlib 相同；40 組隨機輸入的分數與 `Bbox`／`Path` 的方法相同；
    一次繪製只找一次；兩次繪製之間修改文字、資料、字級與座標範圍後畫布仍與 Matplotlib 相同；
    繪製中途發生例外不會留下任何保留的結果。
  - 字型量度：保留的值等於重新計算的值；rcParams、字級、font manager 的字型改變時會重新計算；
    文字範圍與 Python 排版結果和 Matplotlib 相同。
  - KDE：8 種資料量與 bandwidth 的結果與 Matplotlib 逐位元相同；多維、float32、整數、masked 資料沿用原迴圈。
  - 16 種長折線（四種 drawstyle、marker、x 或 y 含 NaN、未排序、`markevery`、對數座標）在放大、平移、
    `set_data`、改 drawstyle 之後都與 Matplotlib 相同。
  - `fork` 的子行程能以多執行緒繪製且結果相同；四個 Python 執行緒同時繪製含圖例的圖，結果與依序繪製相同。
- 只安裝 NumPy 的環境（NumPy 2.2.6）通過 `test_numpy_only.py` 的繪圖比較；
  其中檢查「沒有載入其他套件」的一項在量測用的容器失敗：該容器的 Python 在啟動時就載入自帶的 `sitecustomize` 模組，
  與受測的程式碼無關。

## 限制

- 圖例保留的結果只在單次 `Legend.draw` 之內有效；`tight_layout`、`get_window_extent` 等繪製以外的呼叫沒有變快。
- KDE 的批次只用於一維的 float64 `ndarray`；每組資料超過 4,096 筆時每次只處理一個評估點，與原迴圈相同。
- 量測用的 4 vCPU 虛擬機波動大（同一份程式碼的對照組相差 ±5%，個別案例到 ±12%），
  1.1 倍以下的差異不應視為變快或變慢。
- 測試時另外發現兩件與本次修改無關、0.0.6 已存在的事：renderer 只能在建立它的執行緒使用與釋放
  （在另一個執行緒對同一張圖存檔會失敗）；修改 Axes patch 的 bounds 或 angle 後，繪製結果與 Matplotlib 不同。

## 重跑

```bash
sh scripts/dev_build.sh --locked
export PYTHONPATH="$PWD/python" MPLBACKEND=Agg

python tests/unit/test_fast_paths.py
# 0.0.6 的 python 目錄（已建置 extension）作為對照
python tests/bench/legends.py --rounds 5 --base-source /path/to/matplotlib-rs-0.0.6/python \
    --output tests/output/legends
python tests/bench/basic_charts.py --impls mpl base rs --rounds 5 \
    --base-source /path/to/matplotlib-rs-0.0.6/python --output tests/output/basic-charts
MPLRS_THREADS=1 python tests/bench/basic_charts.py --impls rs --cases scatter --output tests/output/scatter-1
```

環境：CPython 3.13.18、NumPy 2.5.3、Linux x86_64、Intel Xeon Processor @ 2.10GHz、4 vCPU。
中位數、各輪數據與沒有採用的實驗數據見 [`threads-legends-lines.json`](threads-legends-lines.json)。
